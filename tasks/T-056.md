## Examination (2026-06-05)

### Current architecture (single path everywhere)

- `Profile.workingDirectory: string` is the only directory field
  (`src/shared/types.ts`). Workspaces derive their "directories" from
  the union of profile working dirs — no separate field.
- PTY spawns with a single `cwd` (`src/main/pty-manager.ts:340-376`):
  `~` is expanded, then passed straight to `pty.spawn(..., { cwd })`.
  `extraEnv` exists but only injects env vars (Ordna hooks), not paths.
- Built-in agent args (`DEFAULT_AGENTS`, `src/shared/types.ts:210-239`)
  ship **no** directory flags today: claude `--continue`, codex
  `resume`, gemini `--resume`, opencode `[]`.
- Git status (`StatusBar.tsx` → `computeGitStatus(cwd)` in
  `ipc-handlers.ts`) runs against the one profile cwd. No multi-repo.
- ProfileEditor exposes a single text input + Browse + Temp
  (`ProfileEditor.tsx:70-295`).
- Worktree precedent exists: parallel/Kanban agents create a
  `git worktree` per task under
  `~/.config/Vyb/parallel-agents/{profileId}/{taskId}-{shortId}/`
  (`parallel-agent-manager.ts:75-156`) and spawn the PTY with that as
  cwd. **No symlink code anywhere** in the repo today.

### Two approaches

**A. Native multi-dir flags (preferred where supported).**
Pass extra dirs to the CLI directly. Needs per-agent verification, but
to the best of current knowledge:

| Agent    | Native multi-dir support | Flag (VERIFY) |
|----------|--------------------------|---------------|
| claude   | yes                      | `--add-dir <path>` (repeatable) |
| gemini   | yes                      | `--include-directories <a,b,..>` |
| codex    | partial / config-based   | sandbox writable roots in config, no simple flag |
| opencode | unknown                  | — |

This is the clean path: real cwd stays a real git repo, file search
behaves normally. The profile would hold `workingDirectories: string[]`;
the first is the spawn `cwd`, the rest are appended as flags via a
per-agent mapping (extend `AgentConfig` with something like
`extraDirArgs(dirs): string[]`).

**B. Symlink / junction "virtual root" (fallback for agents w/o flags).**
Create a private base dir (e.g. under userData, like the worktree dir)
and link each real path into it, then spawn the agent there.

- Cross-OS: macOS/Linux use `fs.symlinkSync(target, link, 'dir')`.
  **Windows**: plain symlinks need admin/Developer Mode, but
  **directory junctions** (`fs.symlinkSync(target, link, 'junction')`)
  work WITHOUT elevation and are exactly suited to absolute dir links.
  So: symlink on posix, junction on win32 → works on all three.
- Caveats (significant):
  - The virtual root is **not itself a git repo**, so any agent that
    runs `git` from cwd root sees nothing (each linked subdir resolves
    to its own real repo). Breaks the StatusBar assumption.
  - Many tools (ripgrep, and likely agent file indexers) **don't follow
    symlinks by default** → file discovery may silently miss the linked
    dirs. This is the biggest risk and needs a spike per agent.
  - Junctions/symlinks must be cleaned up on profile edit/delete to
    avoid stale links and accidental deletes following a link.

### Recommendation

Lead with **A** (native flags) for claude + gemini; treat **B** as an
opt-in fallback only after a spike proves agents actually traverse the
links for file search. Don't make symlinks the default — the git-root
and search-traversal caveats are likely to surprise users.

## Acceptance Criteria

- [ ] `Profile` carries multiple paths (`workingDirectories: string[]`,
      back-compat with existing single `workingDirectory`).
- [ ] ProfileEditor lets you add/remove/reorder paths (first = primary cwd).
- [ ] Agents with native flags receive extra dirs (claude `--add-dir`,
      gemini `--include-directories`) via a per-agent mapping.
- [ ] Documented, tested behaviour for agents WITHOUT native support
      (either symlink/junction fallback or a clear "single dir only" note).
- [ ] Works on macOS, Linux, and Windows (junctions on win32).
- [ ] No regression for single-path profiles.
