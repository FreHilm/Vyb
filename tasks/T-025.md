## Goal

When a merge / pull / rebase / cherry-pick / revert pauses on a
conflict, the user shouldn't have to open the file in another editor to
resolve it. Build a per-file conflict view that surfaces the three
sides (ours / theirs / base) and lets the user accept one side, accept
both, or hand-edit before staging the resolution.

## Acceptance Criteria

- [x] The in-progress banner (already present for merge / rebase /
      cherry-pick / revert) lists conflicting files with click-through.
- [x] Each conflicting file opens in a conflict viewer with clear
      ours / theirs / base regions and per-hunk "use ours", "use
      theirs", "use both" buttons.
- [ ] An "Edit manually" mode drops into the normal text editor on the
      conflict markers so power users can still hand-edit. *(V2)*
- [x] Resolving the last conflict enables "Continue" in the banner;
      reaching that with no remaining conflicts auto-stages every
      previously-conflicted file.

## Notes

The hard part is parsing `<<<<<<< / ======= / >>>>>>>` markers
robustly and reconstructing the three sides; `git ls-files
--unmerged` + `git show :1: / :2: / :3:` is the clean route.

## Progress

- 2026-05-14: V1 shipped. New `ConflictResolver` overlay in
  `GitChangesPanel`, opened by clicking a file pill in any in-progress
  banner (merge / rebase / cherry-pick / revert). Fetches stages 1/2/3
  via new `git:showStage` IPC, parses working-tree markers (including
  optional diff3 base section), offers per-hunk "use ours / theirs /
  both (ours→theirs) / both (theirs→ours)" actions, writes the merged
  file, then stages it via the existing `gitStage` IPC. Apply button
  gates on every hunk being decided. Manual-edit fallback deferred to
  V2 — power users already have the shell as an escape hatch and the
  one-click resolutions handle the common cases.
